## This week in CSSWG

A quiet week: the 2026-07-08 telecon produced only two resolutions, and the one
that matters to authors tightens how `play()` behaves on a scroll-driven
animation. Everything else is freshly-opened issues — a forms `control-value()`
umbrella and two smaller behavior questions — queued for the F2F rather than
decided.

## Notable

- **Scroll-driven animations: `play()` should re-align a running animation to its scroll range** ([#11469](https://github.com/w3c/csswg-drafts/issues/11469))
  - **Background:** a WPT subtest ("Playing a running animation resets a sticky start time") assumes that calling `play()` on a running scroll-driven animation whose start time was set explicitly should reset that start time (`scroll-animations-1` / `web-animations-2`).
  - **Why it matters:** scroll-driven animations already ship in Chromium and are scriptable through the Web Animations API. Setting an animation's start/current time can push it out of alignment with the scroll range, and `play()` is the natural "re-sync" call — so its exact behavior is directly observable to anyone scripting a scroll or view timeline.
  - **Summary:** implementers noted in the call that Chrome already applies an auto-rewind/auto-align on `play()` that realigns the animation to the scroll range, which is slightly different from what the spec currently says. RESOLVED to [change the spec to meet the comment in the issue](https://github.com/w3c/csswg-drafts/issues/11469#issuecomment-4916924373), bringing the wording in line with that realign-on-`play()` behavior.
  - **Related:** web-animations-2, [Scroll-driven Animations](../features/scroll-driven-animations.md)
