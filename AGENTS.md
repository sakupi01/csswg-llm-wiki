# CSSWG LLM Wiki

An LLM-maintained knowledge base that tracks **how CSS features came to be**: the debates,
resolutions, and status changes of the [CSS Working Group](https://www.w3.org/Style/CSS/),
reconstructed from primary sources so that "why is it like this?" can be answered years later
with citations.

> **Disclaimer**: This wiki is an **unofficial, LLM-maintained synthesis**. It is not a product
> of the CSS Working Group or the W3C. Every claim links to a primary source — verify against
> those sources before relying on anything here. See [Accuracy & Attribution Rules](#accuracy--attribution-rules).

The design follows [Karpathy's LLM-Wiki pattern](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)
as instantiated by [Jxck/tc39-llm-wiki](https://github.com/Jxck/tc39-llm-wiki), adapted for the
CSSWG's data landscape (GitHub issues instead of a minutes repository).

This file is the **single source of truth** for the schema and all workflows.
`.claude/commands/*.md` are pointers into the workflow sections of this file and must not
duplicate procedure. `README.md` is a symlink to this file.

## Layers

| Layer | Path | Written by | Rule |
|---|---|---|---|
| Raw sources | `raw/` | sync scripts only | Immutable input. The LLM reads it, never edits it. |
| Wiki | `wiki/` | LLM only | The compiled knowledge. English. Every claim cited. |
| Generated indexes | `_generated/` | `tools/build_indexes.py` only | Deterministic, greppable. Never hand-edit; re-run the script. |
| Schema | `AGENTS.md`, `tools/` | human + LLM (with review) | Co-evolves as the wiki grows. Schema changes are `[wiki]` commits. |

### Source precedence

When sources disagree, this table decides which one is authoritative:

| Kind of fact | Primary source | Secondary |
|---|---|---|
| Current maturity / TR publication history | `raw/data/w3c-api/specifications/<shortname>.json` (note `snapshot_at`) | https://www.w3.org/TR/ dated URLs |
| Resolution text | css-meeting-bot comment, quoted **verbatim** | `_generated/resolutions-index` |
| Debate narrative, who argued what | The issue thread in `raw/data/github/` | Minutes emails (www-style), `raw/csswg-wiki/` |
| Spec prose | https://drafts.csswg.org/ Editor's Draft (WebFetch) | /TR/ snapshot |
| F2F logistics, agendas, pre-2017 decisions | `raw/csswg-wiki/` | www-style archive |
| Implementation / shipping status | Vendor primary announcements (release notes, Intent threads) | MDN / caniuse (cite anyway) |

Known gaps (do **not** paper over them):

- **1997–2008 minutes are member-confidential** (w3c-css-wg list). This era can only be
  reconstructed indirectly (TR history, www-style technical threads). Say so explicitly.
- Deleted GitHub comments are invisible to the mirror (sync tracks `updated_at` only).
- IRC minutes are a **scribe's paraphrase**, not a transcript (see Accuracy rules).

## Language & style

- Wiki prose is **English**. Resolution text and quotations are verbatim (never translated,
  never paraphrased inside quotation marks).
- Standard relative Markdown links only. **No `[[wikilinks]]`** (VS Code preview compatibility).
- People are referenced as `[fantasai](../people/fantasai.md)`; run `tools/link_people.py`
  after editing. Unknown nicks stay as plain text until mapped in `tools/data/people.yml`.
- Link to raw mirror files with relative paths (`../../raw/data/github/csswg-drafts/issues/08xxx/08350.md`)
  **and** to the GitHub permalink — the mirror for offline grep, the permalink for citation.
- Don't create a page for an entity you haven't read sources for. Unwritten pages are listed
  in `wiki/README.md` under "Not yet ingested" as plain code text (no dead links).
- Formatting is enforced by the PostToolUse hook / pre-commit (2-space indent, trailing
  whitespace stripped, single trailing newline).

## Page schemas

### Feature page — `wiki/features/<slug>.md`

The unit of ingest and the narrative center. A *feature* is the social unit of CSS evolution:
something people champion, debate, and ship (e.g. `css-nesting`, `anchor-positioning`,
`container-queries`), usually spanning many issues and sometimes moving between spec modules.

```yaml
---
title: CSS Nesting
slug: css-nesting
kind: feature
status: shipped        # proposed | in-discussion | specified | shipping | shipped | rejected | superseded
specs: [css-nesting-1]           # current host spec(s)
spec_history:                    # module moves, e.g. masonry: css-grid-3 -> css-masonry-1
  - {spec: css-nesting-1, from: "2021-08"}
key_people: [tabatkins, fantasai]   # people/ slugs; CSSWG has no formal champion role
key_issues: [7834, 8329, 8350]      # issues that carry the narrative
first_seen: "2011-06"               # earliest public trace (issue, www-style, F2F)
resolutions_count: 24               # from resolutions-index; lint checks it (R8)
families: []
coverage: {github: full, www-style: none, member_era: n/a}   # backfill state
generated_by: llm
---
```

Body sections, in order:

1. `## Overview` — 1–3 paragraphs: what it is, why it matters, one-line history.
2. `## Milestones` — table `date | milestone | source`: first proposed → first WG resolution →
   spec adoption → FPWD of host spec → first shipping implementation. Every row cited.
3. `## Resolutions` — chronological table `date | resolution (verbatim) | issue | permalink`.
4. `## Key debates` — one `###` per contested point: the positions, who held them, which
   meeting/issue settled it, and the outcome. This is the heart of the page.
5. `## Related features` / `## Sources`.

Footer (mandatory, verbatim):

> *This page is an unofficial, LLM-maintained synthesis. It is not a product of the CSS
> Working Group. Verify against the linked primary sources.*

### Spec page — `wiki/specs/<shortname>.md`

Thin status ledger; mostly script-assisted. One per spec module the wiki has touched.

```yaml
---
title: CSS Grid Layout Module Level 2
slug: css-grid-2
kind: spec
series: css-grid
level: 2
maturity: CRD                    # normalized code; lint checks against raw/w3c-api (R3)
status_verbatim: "Candidate Recommendation Draft"
first_published: "2018-08-02"
latest_version: "2025-03-26"
ed_url: https://drafts.csswg.org/css-grid-2/
tr_url: https://www.w3.org/TR/css-grid-2/
github_label: css-grid-2
features: [subgrid]
generated_by: llm
---
```

Body: `## Status history` (table `date | status | TR dated URL`, from w3c-api snapshot) +
a mermaid `xychart-beta` line chart of maturity over calendar years, then `## Features tracked here`.

Maturity ordinal for charts: `0 = ED-only, 1 = FPWD, 2 = WD, 3 = CR/CRD, 4 = PR, 5 = REC`.
A CR→WD republication (common in CSS) shows as the line dipping — that is correct, keep it.

Normalized maturity codes: `ED FPWD WD CR CRD PR REC NOTE DNOTE RETIRED DISCONTINUED`.

### Family page — `wiki/families/<slug>.md`

`kind: family`, `members: [<feature slugs>]` (unwritten slugs allowed). Sections: Overview /
Members table / Cross-cutting themes / Related families / Sources. Membership must match the
member features' `families:` frontmatter **bidirectionally** (lint R2).

### People page — `wiki/people/<slug>.md`

Generated by `tools/extract_people.py` from `tools/data/people.yml` + the indexes. Do not
hand-edit; extend `people.yml` and regenerate. Frontmatter: `name, github, irc_nicks,
affiliations [{org, from, to}], roles`. Body: features they appear in, meetings attended,
resolutions they proposed (all generated).

### Meeting page — `wiki/meetings/<YYYY>/<YYYY-MM-DD>-telecon.md`

Frontmatter: `{date, type: telecon|f2f|tpac|unknown, location?, topics_count, issues: [...]}`.
Skeleton (topic list, issue links, verbatim RESOLVED lines) is script-generated from the
meetings index; `/summarise` layers a 3–5 line summary per topic plus links to feature pages.
F2F/TPAC use a directory with per-day files and a `README.md` (attendees, agenda link).

### `wiki/README.md` and `wiki/log.md`

- `README.md`: catalog tables (features / specs / families / recent meetings) with one-line
  summaries, plus a "Not yet ingested" list. Updated by every ingest.
- `log.md`: append-only. One line per operation: `## [2026-07-04] ingest | css-nesting: created feature page (24 resolutions)`.
  Never rewrite history (lint R7 / pre-commit).

## Accuracy & Attribution Rules

Informed by the W3C Group Note [Use of LLMs in Standards Work](https://www.w3.org/TR/llms-standards/).
These rules are hard requirements, enforced by `/lint`:

1. **Label the synthesis.** Every wiki page carries `generated_by: llm` frontmatter and the
   mandatory footer. The repo README opens with the disclaimer.
2. **Cite everything.** Each Key-debate bullet and each Milestones row carries ≥1 source link
   (R4). Link types: resolution → `#issuecomment-<id>` permalink; discussion → issue URL;
   minutes email → lists.w3.org archived-at URL; status → TR dated URL.
3. **Resolutions are verbatim.** Quote the `RESOLVED:` text exactly as the bot recorded it.
   Summaries go outside the quotation, never inside (R1 checks verbatim match to the index).
4. **Minutes are paraphrase.** IRC minutes record what a scribe typed, not what was said.
   For contested points write "the minutes record X as saying …", not "X said …".
   Resolve nicks to real names only through `tools/data/people.yml`; otherwise keep the nick.
5. **Don't guess.** No sources → no claim. Confidential-era gaps are stated as gaps
   (`coverage.member_era`), never filled by inference. Uncertainty is written as uncertainty.

### Lint rules

| # | Check |
|---|---|
| R1 | Every `RESOLVED:` quotation in `wiki/` matches `_generated/resolutions-index.jsonl` verbatim |
| R2 | `feature.specs` ⇔ `spec.features` and `feature.families` ⇔ `family.members` are bidirectional |
| R3 | Spec frontmatter `maturity` / `latest_version` match `raw/data/w3c-api/` |
| R4 | Every Key-debate bullet / Milestones row has a source link |
| R5 | All people links resolve; no nick maps to two people.yml entries |
| R6 | `wiki/README.md` catalog ⇔ actual page set (orphan / missing detection) |
| R7 | `wiki/log.md` is append-only (pre-commit compares against HEAD) |
| R8 | Derived frontmatter values (`resolutions_count`, …) match the indexes |

## Workflows

Commit prefixes: `[ingest] [query] [lint] [summarise] [update] [triage] [backfill]`;
`[wiki]` for schema/structure changes; `[sync]` for commits inside `raw/data/`.
One logical unit per commit. Messages in English, one line.

### Update

Purpose: pull the world forward and report what changed. Run weekly (or before any session).

1. Record current state: `raw/data` submodule SHA, cursors from `.sync-state.json`.
2. Run `python3 tools/sync_issues.py` (incremental — uses saved cursors).
3. Run `python3 tools/sync_w3c_status.py` (fetches only unseen TR versions).
4. `git -C raw/csswg-wiki pull` (and note new F2F pages if any).
5. Commit inside `raw/data` with `[sync] <date>: <n> issues, <m> comments, <k> spec versions`,
   push, then commit the submodule pointer here with `[update]`.
6. Run `python3 tools/build_indexes.py`; commit regenerated indexes in the same `[update]` commit.
7. **Report the diff**: new resolutions since last sync (from resolutions-index), spec status
   changes, new `Agenda+` issues. This report is the weekly digest — show it to the user.
8. Append one line to `wiki/log.md`.

### Triage

Purpose: decide what deserves ingest next. Read-only on `raw/`; writes nothing but a report.

1. From `_generated/`: list (a) issues newly labeled `Agenda+`/`Agenda+ F2F`, (b) resolutions
   in the last N weeks grouped by spec label, (c) spec maturity changes, (d) labels with many
   recent resolutions but **no** feature page (candidates).
2. Cross-check against `wiki/README.md` catalog.
3. Propose: "ingest X (n new resolutions), summarise meetings YYYY-MM-DD…", ranked.
4. Do not ingest anything without the user picking; append the triage note to `wiki/log.md`.

### Ingest — `/ingest <feature | spec shortname | #issue>`

1. **Scope**: grep `_generated/issues-index.md`, `resolutions-index.md`, and
   `_generated/by-spec/<label>.md` for the target; assemble the candidate issue set. State the
   interpretation of an ambiguous target before starting.
2. **Read**: the mirrored threads in `raw/data/github/` (including `<details>` IRC logs in
   bot comments). Large files: read in slices. Note dissent, not just outcomes.
3. **Status**: confirm maturity facts from `raw/data/w3c-api/`.
4. **Write**: create/update the feature page per schema (milestones, verbatim resolutions,
   key debates — all cited). Create/update the host spec page(s). Wire `families` both ways.
5. **People**: add newly prominent participants to `tools/data/people.yml` if identifiable,
   run `extract_people.py` + `link_people.py`.
6. **Catalog**: update `wiki/README.md`; append to `wiki/log.md`. Commit `[ingest] <slug>: …`.

### Query — `/query <question>`

1. Search order: `wiki/README.md` → feature/spec pages → `_generated/` indexes → raw mirror →
   (only if needed) WebFetch drafts.csswg.org / lists.w3.org.
2. Answer with citations (permalinks). Distinguish "the wiki says" from "raw says" from
   "not covered yet".
3. If the answer would be valuable as a page, **ask the user** before writing it back
   (`[query]` commit). Never write back silently.

### Lint — `/lint`

1. Re-run `build_indexes.py` and `extract_people.py` (stale generated content is the most
   common drift).
2. Phase A — internal health: R2, R5, R6, R7, orphan pages, dead relative links.
3. Phase B — source fidelity: R1, R3, R4, R8, treating `raw/` as ground truth ("hunt for
   errors" posture; when wiki and raw disagree, raw wins).
4. Report all findings first; fix after confirmation. Append to `wiki/log.md`. Commit `[lint]`.

### Summarise — `/summarise [YYYY-MM-DD | latest]`

1. Find unprocessed meeting dates in `_generated/meetings-index.md`.
2. Generate the skeleton (topics, issue links, verbatim RESOLVED lines) for each date.
3. Per topic: 3–5 line English summary + link to the feature/spec page if one exists.
   Days of an F2F are independent — parallel processing is fine.
4. Update `wiki/README.md` recent-meetings table; log; commit `[summarise]`.

### Backfill — `/backfill <feature>` (Phase 4+)

Extend a feature's history into the pre-GitHub era.

1. Skeleton from TR history (`raw/data/w3c-api/`), then `raw/csswg-wiki/` F2F pages, then
   `raw/data/www-style/minutes/`, then (last resort) targeted www-style thread fetches.
2. Update the feature's `coverage` frontmatter honestly (`full | partial | none | n/a`).
3. The member-confidential era (1997–2008) is documented **as unavailable** — naming the gap
   is the deliverable, not filling it. Commit `[backfill] <slug>: …`.

## Tools

All Python 3 (stdlib only). GitHub access goes through `gh api --method GET` subprocess calls
(authenticated, 5,000 req/h). W3C API needs no auth (6,000 req/10 min).

| Script | Contract |
|---|---|
| `sync_issues.py [--repo w3c/csswg-drafts] [--full] [--repair] [--dry-run]` | Incremental stream: `/repos/{r}/issues` + repo-level `/repos/{r}/issues/comments`, both `sort=created&direction=asc&since=<cursor>` — created-order is the only stable listing order (sort=updated pages contain outlier items whose displayed `updated_at` disagrees with the hidden sort key, which silently loses items to any windowing scheme). Cursors persist to `.sync-state.json` when a pass completes. `--repair` is the integrity pass: full listing (fits the ~40k deep-pagination cap; full comment history does not) + per-issue comment refetch wherever local count ≠ API count — run it after `--full` and periodically. Rewrites files whole (idempotent). PRs kept only if they carry css-meeting-bot comments. Drops reactions, edit history, label-change events. |
| `sync_w3c_status.py` | Lists CSSWG deliverables via `api.w3.org/groups/wg/css/specifications`, fetches unseen version resources individually, writes normalized `specifications/<shortname>.json` with `snapshot_at`. |
| `build_indexes.py` | Reparses mirror files via comment sentinels only; emits all `_generated/` outputs, sorted and deterministic. Prints the sanity check: issues containing RESOLVED vs. expected order of magnitude (3,324 as of 2026-07). |
| `extract_people.py` / `link_people.py` | people.yml + indexes → `wiki/people/*.md`; auto-link known names/nicks in wiki prose. Unknowns accumulate in `_generated/people-unmapped.txt`. |

Mirror file format (produced by `sync_issues.py`, parsed by `build_indexes.py`):

```markdown
---
number: 8350
title: "..."
state: closed
labels: [css-nesting-1]
author: <login>
created_at: ...Z
closed_at: ...Z
url: https://github.com/w3c/csswg-drafts/issues/8350
comments: 12
has_resolution: true
synced_at: ...Z
---
(issue body)

<!-- comment id=1412345678 author=tabatkins created=2023-01-18T00:00:00Z url=...#issuecomment-1412345678 -->
## @tabatkins — 2023-01-18
(comment body)
```

The HTML-comment sentinel line is the machine contract; body text is never parsed structurally.
Resolution detection: comments by `css-meeting-bot` matching the documented `RESOLVED:` regex
variants (see `build_indexes.py` docstring; 2017–2026 formats differ in backticks and WG naming).
The resolution **date is the comment's `created_at`** — bot comments carry no date in the body.
Async resolutions (label `Async Resolution: *`) are also scanned.

## Scope & phasing

- Current scope: `w3c/csswg-drafts` (+ `w3c/csswg-wiki` as raw). Houdini / FXTF later —
  `sync_issues.py --repo` and the `github/<repo>/` namespace already allow it.
- Initial construction is **foundation + incremental**: indexes cover everything mechanically;
  deep reading happens per-feature via `/ingest`, starting from recent, growing backwards.
- Mirror data lives in the separate public repo
  [sakupi01/csswg-llm-wiki-raw](https://github.com/sakupi01/csswg-llm-wiki-raw) — see its
  `NOTICE.md` (archival purpose, full attribution, takedown contact). If redistribution
  concerns ever escalate, that repo alone can go private without touching this one.
- Wiki content: **CC BY 4.0**; quoted material remains © its authors (see `LICENSE.md`).
